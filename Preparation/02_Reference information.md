## AI駆動開発を加速させるための設計ドキュメント作成ガイド

参照記事を元に、AI（特にClaudeのようなLLMエージェント）があなたの意図を正確に理解し、高品質なコードを生成するための設計ドキュメントの構成と作成方法をまとめました。

これは単なる要約ではなく、各ドキュメントに「何を書くべきか」を具体的に定義した、実践的なテンプレート集です。

---

### はじめに：なぜ事前ドキュメントが重要なのか

AI駆動開発では、AIエージェントに都度指示を出すため、以下のような問題が発生しがちです。

*   **指示の繰り返し:** 同じ設計思想やルールを何度も説明する必要がある。
*   **一貫性の欠如:** AIはファイル単位での最適化は得意だが、プロジェクト全体での統一感を保つのが難しい。
*   **手戻りの発生:** 設計の曖昧さが原因で、後から大規模な修正が必要になる。

これらの問題を解決するのが、**「開発に着手する前に、プロジェクトのルールをすべて言語化しておく」**というアプローチです。AIは優秀な実装者ですが、設計の意図を汲み取るためには、明確な「指示書（ドキュメント）」が必要不可欠なのです。

---

### 1. プロジェクトの司令塔：`CLAUDE.md` の作成

これは、AIエージェントが**常に参照する**最も重要なファイルです。プロジェクトの全体像と、各詳細ドキュメントへのポータルとして機能します。

#### 目的
*   AIエージェントにプロジェクトの全体像、目的、主要なルールを最初にインプットする。
*   タスクに応じて、どのドキュメントを参照すべきかをAIに明確に指示する。
*   開発者が陥りがちな「落とし穴」を事前に共有し、ミスを防ぐ。

#### 記載すべき項目（テンプレート）

```markdown
# プロジェクト名：[あなたのアプリ名] 開発ガイド

## 1. プロジェクト概要と目的
このプロジェクトは「[一言で説明]」するためのアプリケーションです。
主な目的は「[解決したい課題や達成したいこと]」です。
機能要件の詳細は `.claude/00_project/01_appcadia_concept_requirements.md` を参照してください。

## 2. タスク別クイックリファレンスマップ
あなたのタスクに応じて、以下のドキュメントを**必ず**参照してください。

- **新しい機能のロジックを実装する場合:**
  - `01_development_docs/01_architecture_design.md` (アーキテクチャ、責務配置)
  - `01_development_docs/07_type_definitions.md` (型定義)
- **新しいAPIエンドポイントを作成する場合:**
  - `01_development_docs/03_api_design.md` (命名規則、レスポンス形式)
- **UIコンポーネントを作成・修正する場合:**
  - `02_design_system/01_design_principles.md` (色、タイポグラフィ)
  - `02_design_system/02_component_design.md` (コンポーネント設計)
- **テストコードを記述する場合:**
  - `01_development_docs/09_test_strategy.md` (テスト戦略)
  - `03_library_docs/` (ライブラリ固有のテスト方法)
- **エラーハンドリングを実装する場合:**
  - `01_development_docs/06_error_handling_design.md` (エラー分類、処理方法)

## 3. 全体的なルールと制約
- **言語:** TypeScript
- **コーディング規約:** [ESLint, Prettierなど。設定ファイルへのリンクを記載]
- **コミットメッセージ:** Conventional Commitsに従ってください。
- **ブランチ戦略:** GitHub Flowを採用します。

## 4. よくある落とし穴 (最重要)
- **注意1:** Server ComponentsとClient Components間でクラスのインスタンスをpropsとして渡さないでください。シリアライズ不可能なデータは渡せません。
- **注意2:** 環境変数は必ず `process.env` から参照し、クライアントサイドのコードに直接埋め込まないでください。
- **注意3:** [その他、過去にハマったことや、フレームワーク特有の注意点を記載]
```

### 2.1. 技術設計ドキュメント (15個)

開発の根幹をなすルールを定義します。

<details>
<summary><b>01_architecture_design.md</b> - アーキテクチャ設計</summary>

*   **目的:** コードの配置場所（責務）を明確にし、AIが迷わず適切な場所にロジックを実装できるようにする。
*   **記載すべき項目:**
    *   採用アーキテクチャ（例: Clean Architecture, DDD）とその理由
    *   各レイヤーの責務（例: `domain`はビジネスルール、`infrastructure`はDBアクセス）
    *   主要なディレクトリ構成とその説明
*   **AIへの指示例:** 「`01_architecture_design.md` に従って、ユーザー登録機能のUseCaseを実装してください。」

</details>

<details>
<summary><b>02_database_design.md</b> - データベース設計</summary>

*   **目的:** データ構造を定義し、一貫性のあるDB操作をAIに生成させる。
*   **記載すべき項目:**
    *   ER図（Mermaid記法推奨）
    *   各テーブルの詳細な定義（カラム名、データ型、制約、コメント）
    *   命名規則（例: テーブルは複数形、カラムはスネークケース）
    *   インデックス戦略
*   **AIへの指示例:** 「`02_database_design.md` に基づいて、投稿テーブルからデータを取得するPrismaのコードを生成してください。」

</details>

<details>
<summary><b>03_api_design.md</b> - API設計</summary>

*   **目的:** APIエンドポイントの仕様を統一し、フロントエンドとバックエンドの連携をスムーズにする。
*   **記載すべき項目:**
    *   APIスタイル（例: RESTful）
    *   エンドポイントの命名規則（例: `GET /users/{id}`）
    *   リクエスト/レスポンスのJSON形式（成功時・エラー時）
    *   HTTPステータスコードの利用方針
    *   認証方法（例: Bearerトークン）
*   **AIへの指示例:** 「`03_api_design.md` のエラーレスポンス形式に従って、ユーザー作成APIのエラー処理を実装してください。」

</details>

<details>
<summary><b>06_error_handling_design.md</b> - エラーハンドリング設計</summary>

*   **目的:** エラーの処理方法を体系化し、場当たり的な実装を防ぐ。
*   **記載すべき項目:**
    *   エラーの分類（例: バリデーションエラー, 認証エラー, サーバーエラー）
    *   各エラーに対する処理方針（ユーザーへの表示メッセージ、ログレベル、HTTPステータス）
    *   カスタムエラークラスの定義
*   **AIへの指示例:** 「`06_error_handling_design.md` に基づき、フォームのバリデーションエラーを処理するコードを書いてください。」

</details>

> **補足:** 他の技術ドキュメント（画面遷移、SEO、テスト戦略、セキュリティなど）も同様に、「目的」「記載すべき項目」「AIへの指示例」の形式で、プロジェクト固有のルールを具体的に定義していきます。

### 2.2. デザインシステム (5個)

アプリケーションの見た目と操作感の統一性を担保します。

<details>
<summary><b>01_design_principles.md</b> - デザイン原則</summary>

*   **目的:** デザインの基本要素（色、文字、余白）を定義し、AIに一貫したUIを生成させる。
*   **記載すべき項目:**
    *   **カラーパレット:** 用途（primary, secondary, errorなど）と具体的なカラーコード（例: `--primary: #3B82F6;`）
    *   **タイポグラフィ:** フォントファミリー、フォントサイズ、ウェイト、行間のスケール
    *   **スペーシング:** 余白の単位とスケール（例: `space-1: 4px`, `space-2: 8px`）
    *   **ボーダーラディウス:** 角丸のサイズ
*   **AIへの指示例:** 「`01_design_principles.md` のカラーパレットを使用して、プライマリーカラーのボタンコンポーネントを作成してください。」

</details>

<details>
<summary><b>02_component_design.md</b> - コンポーネント設計</summary>

*   **目的:** 再利用可能なUIコンポーネントの仕様を定義し、開発効率と品質を向上させる。
*   **記載すべき項目:**
    *   コンポーネントの分類（例: `atoms`, `molecules`, `organisms` または `ui`, `features`）
    *   各コンポーネントのProps設計方針（命名規則、必須/オプショナル）
    *   状態管理の方針（ローカルステートか、グローバルステートか）
    *   よく使うコンポーネントのバリエーションと使用例
*   **AIへの指示例:** 「`02_component_design.md` に従って、`Card` コンポーネントのバリエーションとして、画像付きのカードを追加してください。」

</details>

*   **AIへの指示例:** 「`02_supabase_auth_vitest.md` の手順に従って、Supabaseのログイン機能をモックした単体テストを作成してください。」

### 3. ドキュメント作成と活用の流れ

1.  **要件定義:** まず、作成するアプリのコンセプトや機能要件を `01_appcadia_concept_requirements.md` のようなファイルにまとめます。
2.  **ドキュメント生成:** 上記のテンプレートを参考に、**AIを使って各ドキュメントのドラフトを生成させます。** 参照記事の著者が行ったように、以下のプロンプトが有効です。

    ```
    # 背景
    これから「[プロジェクト名]」という個人開発アプリを作ります。
    機能要件やコンセプトなどは `.claude/00_project/01_appcadia_concept_requirements.md` にまとめてあります。

    # 目的
    AI駆動開発を効率的に行うため、設計やルールを事前に決めておきたいです。

    # 命令
    添付した参考情報（本ガイドの内容をコピペ）のような構成で、私のプロジェクトに必要な設計ドキュメント一式を作成してください。各ファイルには、私のプロジェクトに合わせた具体的な内容を記述してください。
    ```

3.  **レビューと修正:** AIが生成したドラフトを人間がレビューし、プロジェクトの意図に合わせて内容を具体化、修正します。
4.  **開発開始:** `CLAUDE.md` を起点として、AIに具体的な実装を指示していきます。

### まとめ

AI駆動開発の成功の鍵は、**「AIを、何も知らない新人プログラマーではなく、プロジェクトのルールを熟知した優秀なパートナーとして扱う」**ことです。

今回作成したドキュメント群は、そのための「共通言語」であり「ルールブック」です。最初に時間をかけてこれらのドキュメントを整備することで、開発中の迷いや手戻りが劇的に減り、結果として開発速度と品質が飛躍的に向上します。ぜひ、あなたの次のプロジェクトでこのアプローチを試してみてください。
