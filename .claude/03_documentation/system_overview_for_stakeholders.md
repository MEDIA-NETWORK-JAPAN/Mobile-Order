# Mobile Order System - セッション管理と注文フロー説明書

## 1. システム概要

### 1.1 Mobile Order Systemとは
飲食店向けのモバイル注文システムです。お客様がQRコードをスマートフォンで読み取り、メニューを見ながら注文できる仕組みを提供します。

### 1.2 システムの特徴
```
【3つの注文方法をサポート】
✅ スマートフォン注文 - お客様が自分で操作
✅ ハンディ注文      - スタッフが代行入力  
✅ 混在注文         - 途中で方法を切り替え可能

【高い可用性】
✅ 障害時も営業継続  - インターネット不通でもハンディで対応
✅ 自動復旧       - 復旧後にデータを自動同期
```

## 2. セッション管理の基礎

### 2.1 セッションとは何か
**セッション** = 「お客様の席での1回の利用」を管理する仕組み

```
例：テーブル8番の山田様グループ
┌────────────────────────────────────┐
│ セッション情報                     │
├────────────────────────────────────┤
│ 席番号：テーブル8番                │
│ 利用時間：12:00～15:00             │
│ 人数：4名                         │
│ 注文履歴：ラーメン×2、餃子×3...    │
│ 支払い状況：未会計                 │
└────────────────────────────────────┘
```

### 2.2 2層セッション管理システム

```
          【第1層：席セッション】
          ┌─────────────────────┐
          │   テーブル8番全体   │ 
          │   12:00-15:00      │
          └─────────────────────┘
                    │
        ┌───────────┼───────────┐
        │           │           │
   【第2層：個人セッション】
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │田中さんの│ │佐藤さんの│ │山田さんの│
   │ スマホ  │ │ スマホ  │ │ スマホ  │
   └─────────┘ └─────────┘ └─────────┘

【第1層の役割】同席者で注文履歴を共有
【第2層の役割】個人を識別して不正防止
```

### 2.3 セッションIDの統一管理

```
【重要な設計原則】
すべてのセッションIDは POS端末 で生成します

POS端末 ──生成──→ セッションID ──送信──→ Webサーバー
                SESSION_POS_20240101_120000_08_001
                        ↓
                  URLに変換して返却
                        ↓
                QRコードとして印刷
```

**なぜPOS起点にするのか？**
- **シンプル**: 1箇所で管理するため混乱なし
- **確実**: IDの重複が絶対に起きない
- **障害に強い**: インターネット不通でもPOSは動く

## 3. 注文パターン別フロー

### 3.1 パターン1：スマートフォン注文のみ

```
【お客様の体験】
1. 席に着く
   ↓
2. テーブルのQRコードを読み取る
   ↓  
3. メニューが表示される
   ↓
4. 商品を選んで注文
   ↓
5. 料理が運ばれてくる

【裏側の流れ】
スタッフ操作：POS画面で「席8番、URL発行」
      ↓
POS：セッションID生成 → Webサーバーに送信
      ↓
Web：URLを作成 → POS に返却
      ↓ 
POS：QRコード印刷 → テーブルに設置
      ↓
お客様：QRコード読取 → 注文 → Web → POS → 厨房印字
```

### 3.2 パターン2：ハンディ注文のみ

```
【従来通りの接客スタイル】
1. お客様が席に着く
   ↓
2. スタッフが席に伺う
   ↓
3. 口頭で注文を受ける
   ↓
4. ハンディ端末に入力
   ↓
5. 厨房で調理開始

【裏側の流れ】  
お客様：「醤油ラーメンをお願いします」
      ↓
スタッフ：ハンディで「席8番、醤油ラーメン」入力
      ↓
POS：セッションID生成 → 擬似トークン付与 → 注文データをWebと同期
      ↓
Web：ハンディ注文として記録（個人識別なし）
      ↓
厨房：伝票印字 → 調理開始
```

### 3.3 パターン3：スマホ → ハンディ移行


## 4. 障害発生時の対応

### 4.1 想定される障害

```
【主な障害パターン】
❌ インターネット回線の不通
❌ Webサーバーのダウン  
❌ クラウドサービスの障害

【影響を受ける機能】
❌ スマートフォン注文 → 完全に使用不可
❌ QRコード発行      → 新規発行不可

【影響を受けない機能】  
✅ ハンディ注文      → 通常通り使用可能
✅ POS会計機能      → 通常通り使用可能
✅ 厨房での調理      → 通常通り継続
```

### 4.2 障害時の営業継続方法

```
【お客様への対応例】

お客様：「QRコードが読み込めません」
      ↓
スタッフ：「申し訳ございません。システムの都合で
         お伺いしてご注文を承ります」
      ↓  
スタッフ：ハンディ端末で代行注文
      ↓
お客様：通常通り料理を楽しめる

【売上への影響】
売上機会損失：ほぼゼロ
顧客満足度：軽微な影響のみ
```

### 4.3 障害復旧の自動化

```
【復旧プロセス】

14:00 障害発生
├─ POS：「オフラインモード」表示
├─ ハンディ注文：継続（未同期扱い）
└─ 蓄積データ：POS内に保存

16:00 障害復旧  
├─ POS：自動で接続復旧を検知
├─ 同期処理：未同期データを自動送信
└─ 完了：「通常運用」モードに復帰

16:05 通常運用再開
├─ QRコード発行：再開
├─ スマホ注文：再開  
└─ 売上データ：完全に整合性保証
```

### 4.4 データの完全性保証

```
【障害中のデータ管理】
POS端末内で注文を「未同期」としてマーク
      ↓
【復旧時の自動処理】  
1. 未同期データを検索
2. Webサーバーに一括送信
3. 正常なデータとして記録
4. 売上データに反映
      ↓
【結果】
データロス：0件
売上漏れ：0円  
顧客データ：完全保持
```

## 7. よくある質問（FAQ）

### Q1: 停電時はどうなりますか？
**A:** POS端末にバッテリーがあれば、ハンディ注文で営業継続可能です。電力復旧後に自動でデータ同期されます。

### Q2: お客様がスマートフォンを持っていない場合は？
**A:** スタッフがハンディで代行注文します。従来の接客スタイルと同じです。

### Q3: 注文間違いや変更はできますか？
**A:** スマホ画面で注文確定前なら変更可能。確定後はスタッフにお声がけください。

### Q4: 他のテーブルの注文が見えてしまいませんか？
**A:** セッション管理により、同じテーブルの注文のみ表示されます。セキュリティも万全です。

### Q5: 導入にどのくらい時間がかかりますか？
**A:** 現在のPOSシステムとの連携設定で約2-3週間です。営業を止める必要はありません。

## 8. まとめ

Mobile Order Systemは、**お客様の利便性向上**と**店舗運営の効率化**を両立する次世代注文システムです。

### 8.1 システムの核心価値
```
🎯 柔軟性：3つの注文方法をシームレスに切り替え
🎯 堅牢性：障害時も営業を止めない設計
🎯 簡単性：複雑な操作や研修は不要
🎯 拡張性：将来的な機能追加も容易
```

### 8.2 導入を推奨する理由
1. **immediate Impact（即効性）**: 導入直後から効果を実感
2. **Low Risk（低リスク）**: 既存業務を妨げない設計  
3. **High Return（高い投資効率）**: 短期間で投資回収可能
4. **Future Proof（将来対応）**: 技術進歩に対応した設計

**このシステムにより、お客様により良いサービスを提供しながら、店舗運営の効率化を実現できます。**
